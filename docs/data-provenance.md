| source 值 | 条数 | 说明 |

| 企业内部通知样例 | 1 | 会议通知 |

| 电商平台通知样例 | 1 | 订单发货通知 |

**必须说清楚的三点**：

1. 案例文本是**公开资料的改写**，不是原始执法卷宗，不含任何真实受害人身份信息、真实涉案账号。
2. 部分条目的金额、平台名等细节经过**泛化处理**（如"某电商平台"），目的是保留骗术结构、去掉可识别信息。
3. `source` 字段是**来源类别标注**，不是逐条的原始出处链接。若答辩被追问单条出处，需回溯到公开报道原文，当前未做逐条 URL 存档（见第 6 节局限）。

### 2.3 patterns 来源

依据 10 类骗术的公开套路总结归纳而成，属**自建知识**，每条由人工撰写话术描述 + 关键词数组。

### 2.4 安全案例为何必须存在（问题修复记录）

测试发现：**原知识库 55 条全部是诈骗案例**，导致 RAG 对任何输入都返回诈骗案例——gov.cn 被判「诈骗」、开会通知被判「高危」、工行短信被匹配到 ETC。

根因不是 embedding 能力不足，而是**知识库里没有「正常」这一侧**。向量检索永远返回最近的 K 条，当库里只有诈骗案例时，安全输入只能匹配到诈骗案例。

修复：

- 新增 `银行`（4 条）与 `正常服务`（8 条）两个安全类别，风险标签为 `安全`
- 补充 gov.cn、正常快递、会议通知、12321、12381、运营商提醒、政务办件、电商发货等典型正常文本
- 修复后实测：gov.cn / 开会通知 / 正常快递 / 12321 的 top-1 均为「正常服务·安全」，
  工行与建行短信 top-1 为「银行·安全」，且原诈骗输入的判定无回归

### 2.5 iocs 来源与黑白名单整合（重要）

`iocs` 原表只有"恶意实体"，现已整合为**统一黑白名单**：新增 `list_type` 字段（`white` / `black`），
`value` 上的 UNIQUE 约束保证同一实体只属于一个名单。

**黑名单 23 条（全部为示例数据，使用保留命名空间）**：

- 域名：`.example` 保留顶级域（如 `etc-auth.example`）
- IP：RFC 5737 文档专用地址段（`192.0.2.0/24`、`198.51.100.0/24`、`203.0.113.0/24`）
- 短链：`t.example` / `u.example` / `s.example`

**原因**：反诈库一旦写入真实域名/IP，一旦该域名易主或本身是正常业务，会造成误伤与名誉风险。因此本项目只用不可解析的保留地址演示匹配逻辑，`source` 字段也注明「示例数据（保留域名/文档IP段，非真实恶意地址）」。

**白名单 19 条（真实官方实体）**：

| 类别 | 条目 |
|---|---|
| 政府与公共服务 | `gov.cn`、`12321.cn`、12321、12381、12345、12306 |
| 银行 | `icbc.com.cn`、`ccb.com.cn`、`abchina.com`、`boc.cn`、`cmbchina.com`；95588、95533、95599、95566、95555 |
| 运营商 | 10086、10010、10000 |

白名单记录的是**真实存在的官方域名与客服号码**，这与黑名单正好相反：白名单的价值恰恰在于它必须是真实实体，
才能对"收到的短信是否来自官方"做出确定性判断。

**匹配规则**（`src/lib/rag/iocList.ts`）：

- 域名：解析输入中的 host，做精确匹配或子域名后缀匹配（`www.gov.cn` 命中 `gov.cn`）
- 电话：按非数字边界匹配，避免 `12321` 误伤 `123210`
- URL / 短链 / IP：子串匹配
- **黑名单优先**：同时命中两个名单时按恶意处理（宁可误报不可漏报）

## 3. 判定与检索口径

检索前先做**确定性判定**，再走向量召回：

```
输入
 ├─ 命中黑名单 → 标记「诈骗」，向量检索结果仅作证据补充
 ├─ 命中白名单 → 直接判定「安全」，短路返回（matches 为空，不再召回）
 └─ 未命中     → 走 embedding + 向量检索 + 重排
```

| 项 | 口径 |
|---|---|
| 名单判定 | `iocs.list_type`（white / black），结果经契约① 的 `listMatch` 字段返回 |
| Embedding 模型 | `BAAI/bge-m3`（SiliconFlow 提供） |
| 向量维度 | 1024（与 `vector(1024)` 列定义一致） |
| 案例向量化文本 | `title + "\n" + content` |
| 话术向量化文本 | `pattern + "\n" + keywords.join("、")` |
| 相似度 | 余弦相似度，pgvector `<=>` 运算符，`1 - distance` |
| 召回数量 | 案例 top-K = 5，话术 top-K = 3 |
| 索引 | HNSW（`vector_cosine_ops`），`cases_embedding_hnsw_idx` / `patterns_embedding_hnsw_idx` |
| 重排 | 混合打分：`0.7 × 向量相似度 + 0.3 × 关键词要素重合`；通用词降权 0.3；query 仅含通用词时不重排；配置 `DEEPSEEK_API_KEY` 时额外叠加 LLM 重排（失败自动跳过） |
| 离线兜底 | 内存向量库（`cases-vectors.json` 67 条 + `patterns-vectors.json` 30 条 + `ioc-list.json` 42 条），无网络时退化为关键词打分 |

## 4. 三个置信信号的定义

| 信号 | 公式 | 取值范围 | 含义 |
|---|---|---|---|
| `topSimilarity` | 重排后 top-1 的 `similarity` | [0,1] | 最佳匹配有多像 |
| `labelAgreement` | `Σ sim(与top-1同风险标签) / Σ sim(全部)` | [0,1] | 召回集合的标签一致性（按相似度加权，弱相关案例影响小） |
| `coverageScore` | `命中要素数 / query 要素总数` | [0,1] | 用户输入里的诈骗要素被检索结果覆盖了多少（要素匹配含同义词组，如「抽奖≈中奖」「网贷≈贷款」） |

**口径变更提示**：第 1 周版本中，`labelAgreement` 是标签计数占比、`coverageScore` 是 `命中类别数/3`。第 2 周已按上表重写，**A 侧若按旧口径设过阈值需重新校准**。

## 6. 已知局限（答辩时主动说明，比被问出来更好）

1. **规模有限**：67 条案例（其中安全类仅 12 条）、30 条话术，属演示级知识库。安全案例覆盖面尤其窄，新颖的正常通知仍有被误判可能。
2. **来源未逐条存档**：`source` 是类别标注，未保存每条案例的原始 URL 与抓取时间，严格的可溯源需要补齐这一层。
3. **IOC 为示例数据**：不含真实恶意实体，无法用于真实拦截判定。
4. **LLM 重排未用真实模型验证**：因缺少 `DEEPSEEK_API_KEY`，仅用本地 mock 验证了请求构造、结果解析、超时与降级逻辑，**未验证真实排序质量**，答辩时不应声称其有效。
5. **相似度是语义相似，不是定罪依据**：余弦相似度只反映文本相近程度，与「是否构成诈骗」无法律因果关系。
6. **重排在当前语料上无类别增益**：基线（纯向量）已 100% 命中，重排改变的是排序细节而非类别命中，这一点在自测报告中有如实记录。
7. **安全判定仍是"召回 + 名单"两条腿，但没有相似度阈值**：命中白名单的输入能稳定判「安全」，
   未命中的正常文本仍依赖库里是否有相似的安全案例。后续可加 `topSimilarity < 阈值 → 无法判定` 的兜底。
8. **白名单覆盖有限**：目前只覆盖政府、主要银行、三大运营商与几个公共服务号码，
   地方性机构、二级域名、企业自有通知渠道未收录，这类正常输入仍可能被误判。

## 7. 复现步骤

```bash
# 1. 建表（五个迁移按序执行）
#    supabase/migrations/01_init_tables.sql
#    supabase/migrations/02_match_cases.sql
#    supabase/migrations/03_match_patterns.sql
#    supabase/migrations/04_kb_read_policies.sql
#    supabase/migrations/05_ioc_lists.sql

# 2. 灌入种子数据（幂等，可重复执行）
#    supabase/seed.sql

# 3. 生成向量（bge-m3，1024 维）
npm run embed

# 4. 导出离线快照（案例 / 话术 / 黑白名单）
npx tsx scripts/export-vectors.ts

# 5. 数据体检
npx tsx scripts/audit-data.ts

# 6. 检索质量自测（含 SAFE 正常输入集）
npx tsx scripts/eval.ts

# 7. 验收自检（安全输入 / 银行短信 / 无回归）
npx tsx scripts/verify-safe.ts

# 8. 黑白名单自检
npx tsx scripts/verify-ioc.ts
```

`supabase/seed.sql` 由 `scripts/generate-seed-sql.ts` 从数据库导出，包含全部 139 条记录（67 + 30 + 42），按主键幂等。**它不包含 embedding**：向量由固定文本确定性生成，执行 `npm run embed` 即可重建。
